# Балансировка клиентских подключений хоста

В расширенных настройках хоста есть отдельный источник адресов и стратегия Xray JSON.
`balancer_nodes_source=host` сохраняет прежний порядок: статический `address`, иначе
связанные `node_ids`. В режиме `selected` используются только `balancer_node_ids`
в порядке id; сохранённый статический адрес не участвует. Связанные ноды остаются
независимыми: например, клиент подключается к RU, за которыми HAProxy ведёт к NL.

`ProxyHost` владеет JSON `balancing` и M:N `host_balancer_nodes`. Единый резолвер
`app/xray/host_addresses.py` определяет входные адреса, БС, сужение, пины и снимки.
БС относится к первому сетевому hop, а не первому элементу массива и не downstream.
Tenant-видимость задаётся существующей связью хоста с ботами. Добавление отключённой
ноды запрещено; ранее выбранную отключённую можно оставить при редактировании,
но в выдаче она исключена. Временный статус `error` не исключается: доступность
проверяет клиент. Пустой явный пул исключает хост из всех форматов подписки,
при обновлении кэша пишется предупреждение; подстановки статического/NL-адреса нет.

`balancing=null` означает «из шаблона / по умолчанию»: существующие балансировщики
и наблюдатели сохраняются; multi-address без своего балансировщика получает
прежний `leastPing`. Явная стратегия владеет секциями балансировки в копии конфига:
один `proxy-balancer`, `observatory` для leastPing, `burstObservatory` для leastLoad,
без проб для random/roundRobin. Правила proxy/старых balancerTag перенаправляются
в управляемый балансировщик; условия и порядок direct/block сохраняются.
Шаблоны с несколькими независимыми пулами используйте в режиме шаблона.

- `random` / `roundRobin`: распределение соединений без проверки доступности.
- `leastPing`: выбор наименьшей задержки, проверка через `probe.url` каждые `15s`.
- `leastLoad`: выбор пула по задержке и потерям, по умолчанию expected=2,
  maxRTT=1s, tolerance=0.1, 3 пробы в окне 45s (interval=15s × sampling=3), таймаут 3s.
  expected=0 без baselines — одна нода, maxRTT=0 — без порога. Baselines —
  положительные Go duration, costs — множители по тегам proxy, proxy-1, ….

Другие форматы берут один адрес из того же входного пула. Настройки стратегий
действуют только на Xray JSON, включая случай одного оставшегося адреса.
HAProxy, серверные каскады и распределение серверных пользователей не меняются.

## API и миграция

Новые поля: `balancing`, `balancer_nodes_source`, `balancer_node_ids`. Пропущенные
поля при обновлении существующего хоста сохраняют значение; явный `balancing:null`
сбрасывает стратегию. Создание/переключение в selected требует непустого пула.
Удаление последней ноды не удаляет хост: пустую связь можно оставить при правке
других полей. Весь PUT /hosts сохраняется одной транзакцией; ошибка любого inbound откатывает
весь запрос. Перенос хоста между inbound сохраняет id, настройки и связи.

Миграция `e52ac058ffa1` (после `b47f383fbc9b`) добавляет две колонки и таблицу
составной связи с FK CASCADE и индексом node_id; relationships используют
passive_deletes. Данные прежних хостов не меняются: null/host.
Перед запуском новой версии примените `alembic upgrade head` штатным способом.
Откат `alembic downgrade b47f383fbc9b` удаляет новые настройки и связи; старые
адреса/связанные ноды сохраняются. Перед откатом сохраните новые настройки отдельно.
Не применяйте downgrade при работающей новой версии приложения.

Изолированные тесты проверяют схемы, CRUD, миграцию/откат, выдачу, пины и историю.
Проверка JSON не заменяет сетевой тест двух реальных входов и отказа одного из них
в используемой версии Xray-клиента.

В Xray 26.3.27 пробы распределены по окну interval × sampling; переключение
после отказа не мгновенное. Локальная проверка двух VLESS-входов
(interval=10s, sampling=3, timeout=500ms): 60 запросов
распределились 27/33, после остановки первого и ожидания 45s — 30/30 успешных.
[Реализация burst scheduler](https://github.com/XTLS/Xray-core/blob/v26.3.27/app/observatory/burst/healthping.go).
