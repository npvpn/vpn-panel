# Балансировка клиентских подключений хоста

В расширенных настройках хоста есть отдельный источник адресов и стратегия Xray JSON.
`balancer_nodes_source=host` сохраняет прежний порядок: статический `address`, иначе
связанные `node_ids`. В режиме `selected` используются только `balancer_node_ids`
в порядке id; сохранённый статический адрес не участвует. Связанные ноды остаются
независимыми: например, клиент подключается к RU, за которыми HAProxy ведёт к NL.

`ProxyHost` владеет JSON `balancing` и M:N `host_balancer_nodes`. Единый резолвер
`app/xray/host_addresses.py` определяет входные адреса, БС, сужение, пины и снимки.
БС относится к первому сетевому hop, а не первому элементу массива и не downstream.
Tenant-видимость задаётся существующей связью хоста с ботами. Добавление отключённой
ноды запрещено; ранее выбранную отключённую можно оставить при редактировании,
но в выдаче она исключена. Временный статус `error` не исключается: доступность
проверяет клиент. Пустой явный пул исключает хост из всех форматов подписки,
при обновлении кэша пишется предупреждение; подстановки статического/NL-адреса нет.

`balancing=null` означает «из шаблона / по умолчанию»: существующие балансировщики
и наблюдатели сохраняются; multi-address без своего балансировщика получает
прежний `leastPing`. Явная стратегия владеет секциями балансировки в копии конфига:
один `proxy-balancer`, `observatory` для leastPing, `burstObservatory` для leastLoad,
без проб для random/roundRobin. Правила proxy/старых balancerTag перенаправляются
в управляемый балансировщик; условия и порядок direct/block сохраняются.
Шаблоны с несколькими независимыми пулами используйте в режиме шаблона.

- `random` / `roundRobin`: распределение соединений без проверки доступности.
- `leastPing`: выбор наименьшей задержки, проверка через `probe.url` каждые `15s`.
- `leastLoad`: выбор пула по задержке и потерям, по умолчанию expected=2,
  maxRTT=1s, tolerance=0.1, 3 пробы в окне 45s (interval=15s × sampling=3), таймаут 3s.
  expected=0 без baselines — одна нода, maxRTT=0 — без порога. Baselines —
  положительные Go duration, costs — множители по тегам proxy, proxy-1, ….

Другие форматы берут один адрес из того же входного пула. Настройки стратегий
действуют только на Xray JSON, включая случай одного оставшегося адреса.
HAProxy, серверные каскады и распределение серверных пользователей не меняются.

## API и миграция

Новые поля: `balancing`, `balancer_nodes_source`, `balancer_node_ids`. Пропущенные
поля при обновлении существующего хоста сохраняют значение; явный `balancing:null`
сбрасывает стратегию. Создание/переключение в selected требует непустого пула.
Удаление последней ноды не удаляет хост: пустую связь можно оставить при правке
других полей. Весь PUT /hosts сохраняется одной транзакцией; ошибка любого inbound откатывает
весь запрос. Перенос хоста между inbound сохраняет id, настройки и связи.

Миграция `e52ac058ffa1` (после `b47f383fbc9b`) добавляет две колонки и таблицу
составной связи с FK CASCADE и индексом node_id; relationships используют
passive_deletes. Данные прежних хостов не меняются: null/host.
Перед запуском новой версии примените `alembic upgrade head` штатным способом.
Откат `alembic downgrade b47f383fbc9b` удаляет новые настройки и связи; старые
адреса/связанные ноды сохраняются. Перед откатом сохраните новые настройки отдельно.
Не применяйте downgrade при работающей новой версии приложения.

Изолированные тесты проверяют схемы, CRUD, миграцию/откат, выдачу, пины и историю.
Проверка JSON не заменяет сетевой тест двух реальных входов и отказа одного из них
в используемой версии Xray-клиента.

В Xray 26.3.27 пробы распределены по окну interval × sampling; переключение
после отказа не мгновенное. Локальная проверка двух VLESS-входов
(interval=10s, sampling=3, timeout=500ms): 60 запросов
распределились 27/33, после остановки первого и ожидания 45s — 30/30 успешных.
[Реализация burst scheduler](https://github.com/XTLS/Xray-core/blob/v26.3.27/app/observatory/burst/healthping.go).

## Композиция самостоятельных хостов (NPVPN-2245)

«Сборка из хостов» объединяет подключения разных inbound в один Xray JSON профиль.
Каждый источник сохраняет адрес, порт, транспорт, SNI/TLS/REALITY, path и ключи текущего
пользователя своего протокола. Два хоста с одинаковым IP, но разным SNI остаются разными
участниками. Документы источников не склеиваются: DNS/routing и статические outbounds
берутся из клиентского шаблона получателя.

### Форма и JSON

- `host_injection=null`: наследовать служебный блок шаблона; без него обычный хост.
- `host_injection={"enabled":false}`: обычное подключение даже при инжекте в default.
- `host_injection={"enabled":true,...}`: группы формы полностью заменяют группы JSON.
- `group_tag` — метка группы, отдельная от inbound tag. `is_hidden` скрывает отдельную
  строку подписки во всех форматах, но оставляет источник для инжекта. `is_disabled`
  исключает оба способа выдачи. Hidden не предоставляет доступ к чужому боту/inbound.
- API GET/PUT `/hosts` возвращает read-only `template_injection` для валидации формы
  виртуального получателя с пустым адресом. На запись поле не влияет; форма исключает
  его из payload. При смене шаблона форма пересчитывает метаданные.

Пример корневого блока выбранного клиентского JSON:

```json
{
  "npvpn": {
    "injectHosts": [{
      "selector": {"type":"tagRegex", "pattern":"^MAIN$"},
      "tagPrefix":"proxy",
      "selectFrom":"NOT_HIDDEN"
    }],
    "addVirtualHostAsOutbound":false
  }
}
```

Для явного списка: `"selector":{"type":"ids","values":[12,34]}`.
Также есть `remarkRegex`, `sameTagAsRecipient`; последний не выбирает пустые метки.
Поддерживается алиас `remnawave` вместо `npvpn`, но не оба сразу. UUID Remnawave не
переносятся — используются числовые ID этой панели. Regex использует синтаксис Python,
не JavaScript. Блок обрабатывается панелью и удаляется перед выдачей клиенту.

`selectFrom` — HIDDEN (JSON default), NOT_HIDDEN, ALL. Форма для выбора ID начинает с
ALL. Источники всегда должны быть включены и доступны пользователю. Порядок ID задаёт
порядок подключения; для regex используется `(order,id)`. Сопоставляются сохранённые
remark/group_tag без пользовательских подстановок. В группе ровно один режим тегирования:
`tagPrefix`, `useHostRemarkAsTag:true` или `useHostTagAsTag:true` (fallback на remark).
При префиксе получаются proxy, proxy-2, proxy-3; многoадресный источник занимает несколько
позиций. Старый путь без композиции сохраняет нумерацию proxy, proxy-1.

Собственное подключение получателя по умолчанию не включается. При opt-in оно идёт первым
с тегом proxy; группа proxy продолжает счётчик. Виртуальный источник без собственного
подключения пропускается. Вложенного раскрытия нет: циклы не порождают рекурсию.
Шаблон с инжектом, назначенный default, действует на все наследующие хосты; источникам
в таком случае задают отдельный документ либо override «Обычное подключение».

### Балансировка и ограничения

Существующие balancers в режиме шаблона сохраняются. Без них новый состав получает
управляемый fallback leastPing: перенаправляет правила proxy, пересобирает observatory
по всем участникам с проверкой Google generate_204/15s, сохраняя условия правил и
маршруты direct/block. Явная стратегия формы также включает все группы. Для нескольких
независимых балансировщиков используется режим шаблона. Вспомогательные dialer outbounds
отдельные для каждого endpoint и не входят в managed selector.

Коллизии тегов/опасные префиксы, пустой итоговый пул и ошибки директив не превращаются
в direct-only или собственный fallback. Получатель пропускается с кодом причины в логе;
остальная подписка продолжает выдаваться. Не логируются конфиги и ключи пользователя.
Лимиты: 32 группы, 256 ID в группе, 512 итоговых endpoints, regex до 256 символов,
строка сопоставления до 512, общий deadline regex-выбора 50 мс. Дубли ID запрещены;
повтор источника в разных группах допустим. Неизвестный новый ID отклоняется; удалённый
ранее выбранный ID сохраняется для диагностики и пропускается на выдаче. Новые ссылки
проверяются по итоговому составу всего PUT /hosts: удаляемый в том же запросе источник
недоступен независимо от порядка инбаундов; перенос источника сохраняет его ID.

БС проверяется по настоящему первому hop каждого исходного хоста до сужения. Заблокированный
источник не инжектируется, остальные доступны. Если все доступные источники заблокированы —
одна безопасная заглушка с текстом лимита. Суффикс БС появляется при реально включённом
БС-источнике. Старое поведение обычного хоста с несколькими нодами не меняется.

Сборные получатели поддерживаются только в Xray JSON; URI/Clash/Sing-box их опускают.
В этих форматах остаются обычные видимые источники. Адрес-заглушка виртуального хоста
никогда не выдаётся как рабочее подключение.

### Закрепления, история и миграция

Закрепления/подмножества применяются к исходным хостам одинаково при прямой выдаче
и инжекте. У получателя нет единого списка node_id: его pins/подмножества не действуют,
создание новых pins запрещено; старые записи сохраняются для возврата в обычный режим.
Opt-in собственного endpoint включает его целиком. Hidden-источники можно закреплять
с обычными проверками доступа.

Снимки хранят `is_composite` и `is_hidden`. Композитный snapshot имеет пустой payload;
его история и история скрытого источника — `unknown/restorable=false`, в том числе
после смены режима/возврата видимости. Обычный снимок не доказывает состав пользовательского
сборного документа. Реконструкция полных исторических JSON не реализуется.

Миграция `c45391e22595` следует за `e52ac058ffa1`, добавляет поля хоста и два маркера
снимков; существующие строки остаются обычными/видимыми. Старые API-клиенты без новых
полей сохраняют настройки. Batch upsert остаётся одной транзакцией. Перед downgrade
выключить композицию и убрать служебные блоки из активных шаблонов, включая default;
после отката hidden перестанет действовать. Сначала бэкап. Рабочая БД автоматически
не мигрируется локальными тестами.

Список документов API возвращает `effective_injection` и `effective_injection_error`:
это серверный результат выбора собственного/default/файлового шаблона. Форма использует
его при смене документа, поэтому пустое тело в БД не теряет инжект файлового шаблона.
Метаданные хоста `template_injection` доступны до открытия редактора и не записываются.
Перед выдачей композиции проверяются ссылки routing на outbounds/balancers, fallbackTag,
helper-ссылки и непустое соответствие селекторов итоговым тегам. Проверка выполняется
после применения явной стратегии; корректный ручной шаблон сохраняется.
# Проверка источников в редакторе

«ВЫКЛ» полностью исключает хост из выдачи и из источников сборки. Для источника,
который не должен показываться отдельной строкой, оставьте «ВКЛ» и отметьте
«Скрыть отдельную строку в подписке». Фильтры HIDDEN/NOT_HIDDEN/ALL выбирают только
включённые хосты.

«Проверить источники» в форме и в JSON-редакторе проверяет текущий черновик без
сохранения. В JSON-редакторе выберите получателя: учитываются его тег и явное
переопределение формы. Для каждой группы показаны число/ID источников и причины
пропусков: пустой селектор, выключенный/удалённый хост, фильтр видимости, неактивный
inbound, ошибочная директива или виртуальный источник без собственного подключения.
Пустой JSON использует штатный default/file fallback. При изменении черновика
предыдущий результат исчезает — проверку нужно запустить повторно.

Это диагностика выбора источников, а не Xray dry-run: права пользователя, пины,
БС-лимиты, адреса/ноды и ссылки итогового конфига проверяются при генерации подписки.
