# Архитектура панели NPVPN

Документ описывает то, что не восстанавливается чтением одного файла:
межмодульные связи, сквозные инварианты и грабли. Пересказ того, что и так
видно в коде, сюда не идёт — он устаревает первым и обесценивает документ.

Это входной контекст для AI-ревьюера PR (CodeRabbit, `.coderabbit.yaml`
репозитория бота, `knowledge_base.code_guidelines.filePatterns`), а не
документ для людей в чистом виде.

## Что это за репозиторий

Панель — **форк [Marzban](https://github.com/Gozargah/Marzban), который
обратно в upstream не вливается**. Прямое следствие: «минимальный дифф» не
является ценностью. Рефакторинг затронутого кода — норма, а не повод для
замечания «слишком большой diff»; логика выносится из роутеров (`app/routers/`)
в сервисы (`app/services/`), а не копируется по месту рядом со старым кодом.

Панель живёт в общем рабочем контуре с ботом (`telegram_bot/`). Она не
собирается и не поднимается из своего каталога — образ `marzban` собирается
из исходников `../panel` контекстом в `telegram_bot/docker-compose.override.yml`,
и команды `docker compose build marzban` / `docker compose up` запускаются
из каталога бота, а не отсюда.

## Слои и зависимости

### Пакетное наблюдение активности (NPVPN-2287)

`POST /api/users/activity` — read API интеграций для проверки первого подключения.
Принимает 1–500 username и выбирает только `User.username`, `User.online_at`
одним SELECT, без загрузки ORM-графа, генерации ссылок и изменений токена.
Обычный admin получает только своих пользователей; sudo — запрошенных любого
владельца. Отсутствующая/недоступная строка не означает offline. `online_at=null`
означает существующего пользователя без зафиксированного подключения.
Маршрут отделён в `app/routers/user_activity.py`, запрос — в
`app/services/user_activity.py`. Контракт не меняет digest сверки и полный
UserResponse. Старые клиенты продолжают работать; обновление внешних панелей
добровольно, потребители должны уметь пропускать неподдерживаемое наблюдение.

- `main.py` — uvicorn entrypoint (`main:app`), просто запускает приложение,
  собранное в `app/__init__.py`.
- `app/` — FastAPI-приложение:
  - `routers/` — HTTP-хендлеры (admin, bot, core, home, node, settings,
    subscription, system, user, user_template, managed, memory);
  - `services/` — бизнес-логика (панельные настройки, managed-настройки,
    client apps, дайджест пользователей);
  - `db/` — модели (`models.py`), CRUD (`crud.py`) и собственный alembic
    (`db/migrations/`);
  - `dashboard/` — фронтенд админки (отдельная сборка, node_modules/dist);
  - `jobs/` — периодические задачи (учёт трафика, ревью пользователей и
    BS-нод, снятие просроченных, сброс счётчика трафика пользователей
    (`reset_user_data_usage`), уведомления, пуш xray-конфига);
  - `xray/` — работа с нодами и xray-конфигом (`config.py`, `node.py`,
    `node_config.py`, `operations.py`, каскад ролей, BS-роутинг/лимиты);
  - `telegram/` — уведомления через Telegram (не путать с ботом NPVPN —
    это встроенный в панель Marzban telegram-модуль);
  - `subscription/` — генерация подписочных ссылок и форматов (v2ray,
    clash, singbox, outline и т.д.).
- `config.py` — переменные окружения (`decouple.config`), в т.ч.
  `SQLALCHEMY_DATABASE_URL`, `UVICORN_*`, фичефлаги вроде
  `MEMORY_PROFILING_ENABLED`.

Свой alembic внутри `app/db/migrations/` (`alembic.ini`:
`script_location = app/db/migrations`) — отдельная цепочка ревизий,
независимая от `telegram_bot/src/alembic/`. Миграции панели создаются только
через `alembic revision` в этом репозитории; не смешивать с миграциями бота
и не переносить модели между ними вручную.

## Сквозные инварианты

Каждый инвариант ниже — готовое правило ревью: нарушение почти всегда
означает баг, а не осознанное исключение.

### MySQL, а не Postgres — collation `utf8mb4_bin` на FK к `inbounds.tag`

БД панели — MySQL (`nvb_mysql` в контуре бота), а не Postgres, как у бота.
Внешний ключ на `inbounds.tag` требует явного `collation="utf8mb4_bin"` на
стороне FK-колонки — без этого на MySQL миграция может упасть или завести
рассинхрон с `inbounds.tag` (см. `app/db/migrations/versions/5a20cee1a4e9_*`,
`2c0cafb40725_*`, `a98d3011a530_*`, `c1a7e4b9d2f3_*`,
`dd725e4d3628_fix_mysql_collations.py`). Тест миграции на sqlite это не
ловит — sqlite не проверяет collation FK так, как MySQL, поэтому новая
миграция с FK на `inbounds.tag` должна явно выставлять `utf8mb4_bin` и не
полагаться на зелёный sqlite-прогон как на достаточное подтверждение.

### `users.expire` — `BigInteger`, не `Integer`: потолок `INT32`

`User.expire` (и парный `UserTemplate.expire`) — намеренно `BigInteger`, а не
`Integer`. В MySQL `Integer` — это `INT` с диапазоном до `2147483647`
(2038-01-19 03:14:07 UTC). Бессрочные подписки бота выставляют именно этот
UNIX-потолок как «бесконечность», и любое продление поверх него на `Integer`
роняло `UPDATE` ошибкой `Out of range value for column 'expire'` (NPVPN-1879).
Правило ревью: `expire`-подобная колонка, хранящая unix-timestamp, не должна
объявляться как `Integer` — ни в новой таблице, ни при правке существующей.

### Naive `datetime` — локальное время процесса, хосты в UTC

Как и в боте, naive `datetime` (без `tzinfo`, `datetime.utcnow()` в
`app/db/models.py`) трактуется как локальное время процесса. Продовые
сервера живут в UTC, поэтому сравнение naive-значений из БД с
`datetime.now(UTC)` — источник трудноуловимых расхождений при сверке
(см. также историю дрейфа `expire` при смене таймзоны хоста).

## Ноды и xray

Панель управляет флотом xray-нод: пушит на них конфиг, собранный из
Core settings (`xray_config.json`) плюс пользователей из БД плюс каскадные
добавки по роли ноды (entry/exit/direct, см.
[`cascade-node-roles.md`](cascade-node-roles.md)). Сборка
пользовательской части конфига идёт через `include_db_users()`
(`app/xray/config.py`) — она добавляет к каталожным инбаундам активных
пользователей и кэширует сериализованный per-нодный JSON
(`app/xray/node_config.py`), чтобы не пересобирать его на каждый пуш.

Ключевая ловушка — два разных пути для одного и того же сетевого
sync-вызова к нодам, и они изолированы не одинаково:

- **Защищённый путь.** Реальный сетевой I/O к нодам (gRPC-вызовы xray API)
  идёт через выделенный пул `_xray_executor`
  (`app/utils/concurrency.py`: `ThreadPoolExecutor(thread_name_prefix="xray-pool")`,
  размер — `XRAY_THREAD_POOL_SIZE`), заведённый отдельно от Starlette именно
  для того, чтобы xray-вызовы не делили пул с обработкой HTTP-запросов.
  Попасть в него можно декоратором `@threaded_function` (на функциях
  нижнего уровня — `_add_user_to_inbound`, `_remove_user_from_inbound`,
  `_alter_inbound_user`, `connect_node`, `restart_node` в
  `app/xray/operations.py`) либо прямым `get_xray_executor().submit(...)`,
  как делают джобы (`app/jobs/review_users.py`, `app/jobs/record_usages.py`).
- **Незащищённый путь.** Функции верхнего уровня `add_user`, `remove_user`,
  `update_user` (`app/xray/operations.py`) сами `@threaded_function` не
  помечены — внутри они лишь fire-and-forget раскладывают сетевые вызовы по
  `_xray_executor` через декорированные хелперы, не дожидаясь результата. Но
  из `app/routers/user.py` эти функции целиком планируются через
  `bg.add_task(xray.operations.add_user, ...)` (аналогично для
  `remove_user`/`update_user`) — а `BackgroundTasks` Starlette прогоняет
  sync-колбэк через `run_in_threadpool`, то есть через тот же anyio-пул,
  на котором висят обычные sync-хендлеры. Именно на этом пути уже случалось
  залипание панели: до появления `_get_ready_nodes()` (кэш готовности нод
  только по локальным флагам, без сети) выбор готовых нод шёл через сетевые
  свойства `node.connected`/`node.started`, которые синхронно били по
  каждой ноде и сериализовали вызывающего — одна медленная нода среди ~200
  стопорила этот общий threadpool. Конкретный вызов уже зафиксирован, но
  сам путь диспетчеризации (`bg.add_task` → общий пул) остался, и новый
  синхронный сетевой вызов, добавленный внутри
  `add_user`/`remove_user`/`update_user` в обход `_xray_executor`, повторит
  ту же проблему.

Правило ревью: новый синхронный сетевой вызов к ноде (xray API, gRPC,
`node.connected`/`node.started` и подобные сетевые свойства) обязан идти
через `@threaded_function` или `get_xray_executor()`, а не выполняться
напрямую внутри функции, которую диспетчеризуют через `bg.add_task` из
роутера, — это тот же общий threadpool, что и у обычных HTTP-запросов.
Тяжёлые xray-операции вне запроса планировать по образцу
`app/jobs/review_users.py` (`executor.submit(xray.operations.remove_user, u)`
через `get_xray_executor()`), а не через `bg.add_task`.

Рестарт процесса панели сохраняет REST-сессию управления нодой в
`nodes.control_session_id`: shutdown закрывает локальные транспорты через
`release_local`, не отправляя `POST /disconnect`, а следующий старт подставляет
сохранённый id и восстанавливает gRPC через `try_restore`. При работающем Xray
на ноде этот путь не вызывает `/connect`, `/start` или `/restart`. Явный
reconnect, правка и отключение ноды по-прежнему применяют изменения к удалённому
Xray через штатные вызовы, которые могут прервать пользовательский VPN.

## Клиентские входные пулы хостов

### Информационные хосты

`ProxyHost.is_placeholder` обозначает информационный профиль без рабочего endpoint.
Записью владеет `crud.update_hosts_batch`: при сохранении заглушки очищаются
адрес, клиентский шаблон, аренда, ноды и балансировка; остаются
название, видимость и доступ ботов. Проверка доступа бота предшествует выдаче.
Подписка рендерит такой профиль с нерабочими параметрами средствами формата,
не используя его для инжекта, аренды и биллинга. Outline хранит только один
endpoint, поэтому пропускает заглушки и сохраняет рабочее подключение.
Флаг доходит через готовый кэш хостов без запросов к БД при выдаче подписки.
`GET /api/hosts?exclude_placeholders=true` исключает информационные профили
для списка серверов партнёра; обычная выдача API сохраняет совместимость.


`PUT /api/hosts` сохраняет все переданные inbound одной транзакцией
`crud.update_hosts_batch`. Карта host ID → inbound проверяется до применения:
повторные и неизвестные ID отклоняются. Перенос изменяет ORM-связь существующего
хоста до удаления отсутствующих строк, сохраняя ID, пины, привязки нод/ботов и
дату аренды. Если для существующего ID не передан `order`, сохраняется прежний порядок;
явное значение формы имеет приоритет. Пропущенные ключи inbound не очищаются.
`ProxyHost.inbound` использует `active_history=True`: прежняя связь должна быть
известна ORM, иначе загруженная коллекция `inbound.hosts` может сохранить хост и
впоследствии удалить его через `delete-orphan`. Batch загружает прежние inbound
вместе с хостами, без отдельного запроса на каждый перенос.
Ошибка откатывает весь пакет, включая создание inbound; кэш `xray.hosts`
обновляется роутером только после успешного commit. Формат запроса и sudo-права
не меняются. Синхронизация кэша после commit остаётся отдельной границей отказа.

`ProxyHost` владеет отдельными `balancing` и `balancer_nodes`; прежняя связь
`nodes` независима. Резолвер `host_addresses` задаёт единую семантику адресов,
БС первого hop, пинов и снимков. Генератор подписки читает готовый кэш; запросов
к БД за новыми полями на подписку нет. Это клиентская настройка, не серверная
маршрутизация/HAProxy. Совместимость, инварианты и откат:
[`host-balancing.md`](host-balancing.md).

Диагностика источников — read-only sudo-сценарий `POST /api/hosts/injection/preview`.
`services.xray_templates` накладывает черновик метаданных на каталог БД, строит тот же
default/file lookup и передаёт чистому `xray.host_injection.diagnose_injection`.
Проверка использует общий selector, исключает неактивные inbound и виртуальные источники
без собственного подключения. Она не изменяет ORM/кэш и не поднимает Xray. UI сбрасывает
результат при изменении черновика; ошибки запросов видимы. Проверка выбора источников
не заменяет генерацию для пользователя: credentials, права, pins, БС, доступность нод
и итоговый граф outbound проверяются в существующем пути выдачи.

### Композиция клиентских хостов

`ProxyHost.host_injection/group_tag/is_hidden` задают состав Xray JSON профиля из
самостоятельных endpoints. Форма и JSON-директива имеют один типизированный контракт
`models.host_injection`; форма целиком перекрывает JSON. `xray.host_injection` отвечает
за чистый выбор и ограничения, `subscription.host_candidates` один раз готовит доступные
пользователю endpoints и их БС/подмножества. `v2ray` сериализует их с уникальными тегами
и собственными dialer-ссылками. Документы источников не объединяются, рекурсии нет.

Шаблоны/метаданные кэшируются, пользовательские credentials — нет. Инжект не расширяет
bot/effective-inbound доступы. Hidden не равен disabled. Поля read-only template_injection
в ответе API служат только форме и не являются источником состояния. Изменения сохраняются
в существующей атомарной операции hosts batch; новый source ссылается только на сохранённый ID.

Классификатор композиции в существующем сервисе `xray_templates` использует тот же resolver
для pins, снимков и истории (default/file fallback включён). Снимки имеют исторические
маркеры composite/hidden: их отсутствие среди реконструируемых payload означает unknown,
а не пустой подтверждённый набор. Пины относятся к исходным хостам; получатель не создаёт
фиктивный набор node_id из разнотипных подключений. Полный контракт и rollback — в
[`host-balancing.md`](host-balancing.md).

### Ручная сверка трафика хостинга

`node_hosting_traffic_adjustments` хранит аудируемые поправки к NIC, отдельно
от raw `node_hosting_nic_daily`. UUID — ключ повтора; `created_at` UTC
определяет календарный день/месяц MSK. Отмена заполняет `cancelled_at` и
`cancel_reason`, запись не удаляется. При чтении daily складываются raw и
активные поправки диапазона; окончательный расход неотрицателен.
`hosting_used_bytes` MTD уже содержит поправки от внешнего сборщика, поэтому
fallback не прибавляет их повторно. Если raw daily отсутствует, одна
поправка не создаёт NIC-итог: неизвестный raw не равен нулю. Иначе
частичный offset подавил бы полный скорректированный MTD fallback
(например, показал бы 50 вместо 150). Учёт пользователей и partner billing
этот журнал не читает. Инфраструктурный CLI в общем рабочем контуре владеет
транзакцией записи и сериализует корректировки одной ноды через её row lock;
панель только читает журнал. Изменений публичного API нет. Миграция журнала
должна быть применена до обновления сборщика; отсутствие таблицы — ошибка,
а не разрешение отбросить поправки.


### Идемпотентная доставка купленных ГБ

`POST /api/user/{username}/bs-extra` принимает необязательный UUID `operation_id`.
`crud.modify_user_bs_extra` владеет транзакцией: до receipt INSERT блокирует строку
пользователя, затем сохраняет receipt и изменение пула одним commit. Повторный UUID
не начисляет ГБ заново; после конфликта receipt читается locking/current read,
чтобы увидеть чужой commit даже из старого MySQL REPEATABLE READ снимка. UUID с
другим пользователем или количеством байт отклоняется. Старые клиенты без UUID
сохраняют прежний контракт. Проверки конкурентных покупок и повторов используют
отдельный тестовый MySQL, а не рабочие данные.


### Ограниченные операции нод и свежесть учёта (NPVPN-2387)

Admission подключения/рестарта принадлежит process-local NodeOperationScheduler.
Очередь хранит ID, вид команды, время и общий Future; полный пользовательский
конфиг туда не попадает. В executor передаются только свободные slots, не более
XRAY_NODE_CONNECT_CONCURRENCY. Один node_id имеет активную операцию и не более
одного объединённого следующего намерения; фоновые сигналы объединяются с активным,
каждый ручной запрос сохраняет следующее намерение даже за ещё не стартовавшей
командой, поскольку shared snapshot её группы мог быть построен другим worker. Snapshot конфига лениво строится внутри
исполняемой группы, не кэшируется между волнами и освобождается с работой. Успешный SOFT restore вообще
не материализует пользовательский snapshot.
Отмена ещё не стартовавшей команды сохраняет физический slot до прохода executor,
чтобы серия cancel/resubmit не создала новую неограниченную очередь.

Существующий xray-pool обслуживает пользовательские команды; node-control и
node-usage используют отдельные ограниченные пулы. Usage имеет W=XRAY_THREAD_POOL_SIZE,
не более W in-flight чтений на каждую из двух существующих задач с max_instances=1.
Eligibility читает локальные started/session/API flags без REST ping; реальные
ошибки API возвращаются как ошибка ноды, а не пустой успешный ответ. Результаты
записываются по завершению без удержания всех node delta и ожидания медленного
первого запроса. Суммы User/Admin/System, hourly history и БС сохраняют коэффициенты
и формат; запись по завершившейся ноде увеличивает число небольших SQL batch вместо
одного общего batch. Metadata БС читается до reset=True: при недоступной БД сбор
не забирает счётчик, который ещё не знает как записать.

Успешный учёт означает успешный API и все включённые этапы записи конкретной ноды.
Пустой успешный ответ тоже обновляет freshness, ошибки API/БД — нет. Старые
разнотабличные инкременты не становятся общей транзакцией: после частичной ошибки
delta автоматически не повторяется, иначе возможен двойной расход. Такие ошибки
имеют отдельные метрики/лог, а историческая разбивка по часам не восстанавливается.

Edit/Disable сохраняют желаемые параметры и `nodes.config_apply_pending` одной
транзакцией, без RPC и ожидания активной команды в HTTP. Под metadata lock
строка перечитывается current/locking read (`refresh(..., with_for_update=True)`),
поэтому ORM-снимок HTTP до предыдущего ack не теряет новое pending/Connecting.
Создание inbound/default host внутри edit делает flush, итоговый commit один. Тот же ограниченный
планировщик исполняет приоритетный APPLY: пересоздание transport и HARD для
включённой ноды, stop и disconnect без запуска Xray для Disabled. Повторные правки объединяются;
параметры читаются при исполнении. Старая команда уступает после текущего RPC,
не продолжает retry и не публикует старый статус/сессию. Сохранение и публикации
сериализованы коротким per-node metadata lock без RPC/полного config build.
Успех актуального APPLY снимает флаг; ошибка оставляет флаг и причину в status/
message. Startup и существующий health-check подхватывают pending, включая
Disabled; остальные ноды восстанавливают сохранённую сессию обычным SOFT.
Recovery повторно проверяет pending под metadata lock до pause/admission: старый
health snapshot не запускает лишний HARD и не оставляет учёт paused после ack.
Такие восстановления ставятся в обычный FIFO существующего scheduler и не
расходуют лимит обычных health-reconnect на тик; исполняемых slots не прибавляется.
При отключении после рестарта сначала восстанавливается control transport с
сертификатом ноды, затем stop/disconnect; start/restart не выполняется. Сохранённая
сессия очищается только подтверждённым remote disconnect, как и до исправления.

Delete сохраняет отдельный admission guard: активная операция или запись
accounting — 409 до DB write; ожидающая команда отменяется. Возраст stale не
освобождает живую sync-команду. Сохраняются session/lifecycle locks NPVPN-2373;
shutdown сначала завершает ограниченные node operations, затем отпускает локальные
transport без остановки удалённого Xray.

Prometheus читает только in-memory snapshots новых метрик. last_success/tracking_since,
accounting_delay и delay_threshold экспортируются по name/kind ещё до первого успеха,
удалённые/disabled ноды уходят из snapshots, поколение не даёт старому результату
освежить повторно включённую ноду. Успешные edit/disable/delete явно снимают
ownership freshness, не ожидая периодического наблюдения disabled. Revision
снимается до DB read; устаревший metadata snapshot отклоняется до reset=True,
следующий существующий тик повторяет чтение. Конкурирующее редактирование может
отложить один проход, но не забирает и не теряет необратимую delta. Budget=2*period+ceil((enabled+1)/W)*(30s+10s):
обе usage-задачи разделяют пул, а основной core тоже занимает запрос. Задержка БД
не продлевает budget. Общая свежесть тика не подменяет per-node состояние.

Центральный Grafana alert в telegram_bot включается после обновления панели.
Он сравнивает delay/budget для connected primary нод. Здоровые ряды возвращают0,
отсутствие ожидаемо работающих нод тоже0; отсутствие новых метрик при работающих
нодах остаётся NoData. Установки без центрального мониторинга используют те же
экспортируемые метрики для собственного алерта.

### Accounting и изменение ноды

`app/services/node_lifecycle.py` владеет edit/delete. Edit закрывает допуск
новых reset и инвалидирует снимки metadata/freshness; существующие collection
leases доводятся до SQL-записей с прежним коэффициентом и БС-владением. Одна
callback готовности на ноду допускает APPLY после освобождения последнего lease;
повторные edit заменяют callback. Отказ БД восстанавливает прежний допуск и не
отменяет прежнюю команду. Delete проверяет accounting до отмены reconnect.

`UsageState` проверяет epoch непосредственно перед reset. Lease сохраняется через
получение delta, все SQL-записи и отметку свежести; при edit delta не отбрасывается
и не сбрасывается повторно. Новые snapshots исключают paused-ноду до актуального
APPLY; старый результат не освежает новую конфигурацию. Registry mutex не держится
при RPC/SQL/callback. `completed_results` освобождает lease после обработки, также
при позднем завершении futures после закрытия consumer. SQL-потребитель остаётся
единственным для каждого вида статистики.

Пулы node-control и node-usage создаются при импорте модуля; потоки появляются только
при submit. Одновременный первый вызов jobs не может создать второй usage-pool.
